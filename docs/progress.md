## 4分割問題：調査再開と新知見（2026-08-26 続報）

引き渡し資料を一度完成させた後、ユーザーの希望で4分割問題の調査を再開した。以下の重要な新知見が得られた。

| 検証内容 | 結果 |
|---|---|
| 本物のQRデータの黒画素密度を測定 | 約8.6%（真っ黒ではなく疎なハーフトーン網目）。均一な塗りつぶしは一切使われていない |
| ノートエディタで「QRコードを4つ手動で横並び」に配置し実際に印刷・キャプチャ | 384×348pxの1ジョブとして送信され、複雑な内容でも実データは常に正常動作することを再確認 |
| 「左半分だけ黒」のシンプルな画像を送信 | 紙面に**均等間隔で4つの小さな黒い四角**が印字された（画像全体が縮小されて4回複製されたような結果） |
| 密度をハーフトーン風に下げる、行数を実データ規模まで拡大する等、複数の組み合わせテスト | 分割数が3個・2個・1個と変化する場合もあったが、安定して「1個・正しいサイズ・正しい縦横比」を同時に満たす組み合わせは発見できず |

**新しい仮説（有力）:** プリンターは384px幅を **4つの96px区画に物理的に分割して処理**しており、
自前生成データ（384px幅の1本の連続したビットマップ行）は、その4区画それぞれに「圧縮コピー」
されてしまっている。本物のアプリは384px幅いっぱいの内容を4区画それぞれに向けて個別にフォーマット
して送信していると推測されるが、正確なデータ配置方法（インターリーブか、区画ごとの個別ヘッダーか等）
は未解明。詳細は `docs/protocol_spec.md` の「既知の未解決問題」セクションを参照。

文字印刷が実用上問題なく見えるのは、生成される文字画像の幅が384px全体を使わないことが多く、
4分割・圧縮の影響が視覚的に目立たないためと推測される。

## 4分割問題：決定的な追加発見（2026-08-26 続報2）— バイト値が実は16通りしかない

`captures/rfcomm_jobs/`の全実キャプチャ（文字18件＋QR単体2件＋ノートエディタの4連結QR実データ
`job4up_native.bin`、計198,528バイト）のビットマップ本体を1バイト単位で統計調査した結果、
**実際に出現するバイト値は256通り中わずか16通り**（`0x00,0x01,0x02,0x03,0x10,0x11,0x12,0x13,
0x20,0x21,0x22,0x23,0x30,0x31,0x32,0x33`＝上位/下位ニブルとも常に0〜3の範囲）のみだと判明した。
`0xFF`（8画素連続黒）はQRのファインダーパターンのような本来ベタ塗りのはずの部分でも一度も
出現しない。統計的に偶然ではあり得ない（ランダムなら`0xFF`だけでも約780回出現する期待値）ため、
明確なフォーマット上の制約が存在すると判断した。

一方、私たちの`printer/qr.py`・`printer/image.py`が生成するビットマップは256値すべてを自由に
使っており、実データの値域から完全に外れている。**これが4分割バグの直接原因である可能性が高い**
という仮説のもと、生成データの各バイトに`0x33`でANDマスクをかけ実データと同じ値域に収める実験用
スクリプト`tools/experiments/mask_test.py`を作成した（`--save-only`でファイル保存のみ、通常は
COMポートへ直接送信可能）。まだ実機テストは未実施。

正しいビット→画素の対応関係（1バイトに2画素だけ実在するのか、2bit階調値が2個埋め込まれているか等）
はまだ確定していない。試しに「1バイト＝2個の2bit階調値（96px幅相当）」としてデコードしてみたところ、
文字「A」はほぼ正しい縦横比で復元できた一方、QRコードは縦横比が大きく崩れており、この解釈だけでは
説明が付かない部分が残っている。詳細は`docs/protocol_spec.md`参照。

## mask_test.py 実機検証の結果（2026-08-26 続報3）: 否定的

`tools/experiments/mask_test.py`を実機（COM3）で実行し、生成QRの各バイトを実データと同じ
「16値ドメイン」に収めた状態で送信してもらった。**結果: 依然として横に4分割され、情報量が
減った分サイズも小さくなった。** よって「バイト値が256通り自由に使われていること」単体は
4分割の直接原因ではないと判定し、この仮説は棄却した（詳細は`docs/protocol_spec.md`）。

あわせて、`job4up_native.bin`（本物のアプリの「QR4つ横並び」実データ）を1bit/384px幅の前提で
再レンダリングしたところ、期待していた「横4列」ではなく縦方向に3分割されたような模様が見え、
従来の解釈だけでは説明が付かない部分が残っていることも判明した。
