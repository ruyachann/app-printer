02 手順書との主な相違点

元の手順書は BLE + bleak を前提としていたが、実機解析の結果いくつかの前提が覆った。判断の根拠は全て docs/progress.md の決定事項ログに残している。

手順書の前提実際の調査結果対応
Bluetooth Low Energy（bleakで実装） Android側では"BLE"を含む名前（PPS1_DD4C_BLE）で見えるが、実データ通信は Bluetooth Classic（RFCOMM/SPP）。ATT/GATTパケットは全キャプチャ中0件。Windows側のペアリング済み一覧では"_BLE"接尾辞なしのPPS1_DD4Cと表示される Python標準の socket.AF_BLUETOOTH（Windowsでは pyserial経由のCOMポート接続）に変更
Wiresharkで手動解析 btsnoopログを直接アップロードしてもらい、自作Pythonパーサーで解析する方が高速・確実だった tools/btsnoop_parser/ を新規実装
文字とQRの通信を比較して判定 専用アプリにQR機能が(当初は)見当たらず、後に「ノートエディタ」内に発見。最終的に両方とも同一の画像プロトコルと確認 QRは専用コマンドなしと結論、画像プロトコルに統一
画像テスト(白/黒ドット/線/四角)で画像仕様を特定 解析用端末(Android 7.0)の性能不足で画像メニューが開けず未実施 ビットマップ通信解析に加え、本物のアプリのAPKを逆コンパイルして画像エンコード処理のソースコードを直接確認する手法に切り替え

03 確定した通信プロトコル

印刷ジョブは3部構成。文字・QR・画像とも専用コマンドは存在せず、共通の4階調グレースケールラスターとして送信される。

Header
8 bytes
Bitmap
height × 192 bytes
Footer
10 bytes

RFCOMM上を約240バイト単位のUIHフレームに分割して送信（Bluetooth Classic / SPP、DLCI=2）。

1D 47 59 ‹gray_levels=04› ‹width_ref u16 LE=30 00› ‹height u16 LE› ... 1B 4A 50 1B BB BB 10 FF F1 45
ビットマップ仕様（2026-08-26 訂正版）
幅384 px
1行あたりバイト数192 bytes（1バイトに2画素、4bit/画素）
形式4階調グレースケール（値0〜3、0=白・3=黒）
高さヘッダー内の値そのまま（変換不要）。文字は常に23行固定、QR・画像は内容に応じて可変

この仕様は実機テストで最終検証済み: 文字・QR・画像のいずれも1個だけ、歪みなく正しく印字されることを確認した。tests/test_protocol_replay.py では、実キャプチャの中身から再構成したコマンドが元のバイト列と完全一致することを自動テストで保証している。

04 最大の難関だった不具合とその解決

⚠ 調査序盤〜中盤：QRコード等の自前生成画像が紙面に横4分割される

自前で生成した画像データを送信すると、紙面に本来1枚のはずの画像が横4分割されて印字される現象が長期間発生していた。実際にアプリが送信した本物のデータをそのまま再送すると常に正しく1つだけ印字されるため、原因は「生成した画像データの中身」にあると推測されたが、以下の要因を実機で個別に切り分けても特定できなかった。

切り分けた要因結果
送信経路（COMポート接続・チャンク分割等）無関係
データサイズ・行数無関係
バイト値の範囲・パターンの複雑さ無関係
送信幅・余白（マージン）無関係

決め手となった手法：本物のアプリのAPK逆コンパイル

ブラックボックスの通信解析だけでは原因が特定できなかったため、方針を切り替え、本物のアプリ（com.dingdang.newprint）のAPKファイルを端末から取得し、逆コンパイルした（androguardというPython製ツールを使用）。その結果、com.luckprinter.sdk_newという専用プリンターSDKの中に、実際のビットマップ変換処理（PrinterImageProcessorクラス）を発見した。これにより、プロトコルの理解が根本的に誤っていたことが判明した。

従来の誤った理解

1bit白黒（8画素/バイト）

48バイト/行

高さフィールド ×4 = 実際の行数

正しい仕様

4階調グレースケール（2画素/バイト）

192バイト/行

高さフィールド = そのまま実際の行数

48×4=192という数値が偶然一致していたため、「ヘッダーの高さ×4＝実際の行数」という辻褄の合う（しかし誤った）解釈のまま長期間実装・検証を続けてしまっていた。総バイト数はどちらの解釈でも変わらないため、単純なバイト列再構築テストでは矛盾を検出できず、実機に自前生成画像を送って初めて不具合として露呈していた。正しい形式で実キャプチャデータを再デコードしたところ、文字・QR・複数QR配置のいずれも歪みのない正しい画像として復元でき、この発見が正しかったことが裏付けられた。

✓ 修正と実機確認

printer/protocol.py・printer/image.py・printer/qr.pyを正しい仕様に全面的に書き直し、実機でテストした結果、QRコード（きれいな大きなQRコードが1個だけ）、文字（日本語を含め読める大きさで）、画像（写真）（グレースケール写真をFloyd-Steinbergディザリングで自然な階調表現に）のいずれも正しく印字されることを確認した。写真の初回テストではグラデーション部分に4階調ゆえの縞模様（バンディング）が出たが、ディザリングを標準で有効にすることで解決した。
