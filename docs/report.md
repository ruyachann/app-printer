## 2. 手順書との主な相違点

元の手順書は BLE + `bleak` を前提としていたが、実機解析の結果いくつかの前提が覆った。
判断の根拠は全て `docs/progress.md` の決定事項ログに残している。

| 手順書の前提 | 実際の調査結果 | 対応 |
|---|---|---|
| Bluetooth Low Energy（`bleak`で実装） | デバイス名に "BLE" を含むが、実データ通信は **Bluetooth Classic（RFCOMM/SPP）**。ATT/GATTパケットは全キャプチャ中0件 | Python標準の`socket.AF_BLUETOOTH`（Windowsでは`pyserial`経由のCOMポート接続）に変更 |
| Wiresharkで手動解析 | btsnoopログを直接アップロードしてもらい、自作Pythonパーサーで解析する方が高速・確実だった | `tools/btsnoop_parser/` を新規実装 |
| 文字とQRの通信を比較して判定 | 専用アプリにQR機能が(当初は)見当たらず、後に「ノートエディタ」内に発見。最終的に両方とも同一の画像プロトコルと確認 | QRは専用コマンドなしと結論、画像プロトコルに統一 |
| 画像テスト(白/黒ドット/線/四角)で画像仕様を特定 | 解析用端末(Android 7.0)の性能不足で画像メニューが開けず未実施 | ビットマップ通信解析に加え、**本物のアプリのAPKを逆コンパイル**して画像エンコード処理のソースコードを直接確認する手法に切り替え |

## 3. 確定した通信プロトコル

印刷ジョブは3部構成。文字・QR・画像とも専用コマンドは存在せず、共通の**4階調グレースケール
ラスター**として送信される。

```text
┌──────────────┬─────────────────────────────┬──────────────┐
│  Header      │  Bitmap                      │  Footer      │
│  8 bytes     │  height × 192 bytes           │  10 bytes    │
└──────────────┴─────────────────────────────┴──────────────┘
```

RFCOMM上を約240バイト単位のUIHフレームに分割して送信（Bluetooth Classic / SPP、DLCI=2）。

```text
1D 47 59 <gray_levels=04> <width_ref u16 LE=30 00> <height u16 LE> ... 1B 4A 50 1B BB BB 10 FF F1 45
```

### ビットマップ仕様（2026-08-26 訂正版）

| 項目 | 値 |
|---|---|
| 幅 | 384 px |
| 1行あたりバイト数 | **192 bytes**（1バイトに2画素、4bit/画素） |
| 形式 | **4階調グレースケール**（値0〜3、0=白・3=黒） |
| 高さ | ヘッダー内の値そのまま（変換不要）。文字は常に23行固定、QR・画像は内容に応じて可変 |

この仕様は実機テストで最終検証済み: 文字・QR・画像のいずれも1個だけ、歪みなく正しく
印字されることを確認した。`tests/test_protocol_replay.py`では、実キャプチャの中身から
再構成したコマンドが元のバイト列と完全一致することを自動テストで保証している。

## 4. 最大の難関だった不具合とその解決

> **調査序盤〜中盤: QRコード等の自前生成画像が紙面に横4分割されて印字される問題**
>
> 自前で生成した画像データを送信すると、紙面に本来1枚のはずの画像が**横4分割**されて
> 印字される現象が長期間発生していた。実際にアプリが送信した本物のデータをそのまま
> 再送すると常に正しく1つだけ印字されるため、原因は「生成した画像データの中身」に
> あると推測されたが、以下の要因を実機で個別に切り分けても特定できなかった。

| 切り分けた要因 | 結果 |
|---|---|
| 送信経路（COMポート接続・チャンク分割等） | 無関係 |
| データサイズ・行数 | 無関係 |
| バイト値の範囲・パターンの複雑さ | 無関係 |
| 送信幅・余白（マージン） | 無関係 |

### 決め手となった手法: 本物のアプリのAPK逆コンパイル

ブラックボックスの通信解析だけでは原因が特定できなかったため、方針を切り替え、
**本物のアプリ（`com.dingdang.newprint`）のAPKファイルを端末から取得し、逆コンパイル**
した（`androguard`というPython製ツールを使用）。その結果、`com.luckprinter.sdk_new`という
専用プリンターSDKの中に、実際のビットマップ変換処理（`PrinterImageProcessor`クラス）を
発見した。

これにより、**プロトコルの理解が根本的に誤っていた**ことが判明した。

| | 従来の誤った理解 | 正しい仕様 |
|---|---|---|
| 画素形式 | 1bit白黒（8画素/バイト） | **4階調グレースケール（2画素/バイト、4bit/画素）** |
| 1行のバイト数 | 48バイト | **192バイト** |
| 高さフィールド | ×4して実際の行数 | **そのまま実際の行数** |

48×4=192という数値が偶然一致していたため、「ヘッダーの高さ×4＝実際の行数」という
辻褄の合う（しかし誤った）解釈のまま長期間実装・検証を続けてしまっていた。総バイト数は
どちらの解釈でも変わらないため、単純なバイト列再構築テストでは矛盾を検出できず、
実機に自前生成画像を送って初めて不具合として露呈していた。

正しい形式で実キャプチャデータを再デコードしたところ、文字・QR・複数QR配置のいずれも
歪みのない正しい画像として復元でき、この発見が正しかったことが裏付けられた。

### 修正と実機確認

`printer/protocol.py`・`printer/image.py`・`printer/qr.py`を正しい仕様に全面的に
書き直し、実機でテストした結果:

- **QRコード**: きれいな大きなQRコードが1個だけ正しく印字されることを確認
- **文字**: 日本語を含む文字が読める大きさで正しく印字されることを確認
- **画像（写真）**: グレースケール写真を印刷したところ、初回はグラデーション部分に
  4階調ゆえの縞模様（バンディング）が出たが、Floyd-Steinbergディザリングを標準で
  有効にすることで解決し、自然な階調表現で正しく印字されることを確認
