## 2. 手順書との主な相違点

元の手順書は BLE + `bleak` を前提としていたが、実機解析の結果いくつかの前提が覆った。
判断の根拠は全て `docs/progress.md` の決定事項ログに残している。

| 手順書の前提 | 実際の調査結果 | 対応 |
|---|---|---|
| Bluetooth Low Energy（`bleak`で実装） | デバイス名に "BLE" を含むが、実データ通信は **Bluetooth Classic（RFCOMM/SPP）**。ATT/GATTパケットは全キャプチャ中0件 | Python標準の`socket.AF_BLUETOOTH`（Windowsでは`pyserial`経由のCOMポート接続）に変更 |
| Wiresharkで手動解析 | btsnoopログを直接アップロードしてもらい、自作Pythonパーサーで解析する方が高速・確実だった | `tools/btsnoop_parser/` を新規実装 |
| 文字とQRの通信を比較して判定 | 専用アプリにQR機能が(当初は)見当たらず、後に「ノートエディタ」内に発見。最終的に両方とも同一の画像プロトコルと確認 | QRは専用コマンドなしと結論、画像プロトコルに統一 |
| 画像テスト(白/黒ドット/線/四角)で画像仕様を特定 | 解析用端末(Android 7.0)の性能不足で画像メニューが開けず未実施 | 文字・QRキャプチャのビットマップパターンから画像仕様を逆算し代替 |

## 3. 確定した通信プロトコル

印刷ジョブは3部構成。文字・QRとも専用コマンドは存在せず、共通の1bitラスタービットマップとして送信される。

```text
┌──────────────┬─────────────────────────────┬──────────────┐
│  Header      │  Bitmap                      │  Footer      │
│  8 bytes     │  height × 48 bytes           │  10 bytes    │
└──────────────┴─────────────────────────────┴──────────────┘
```

RFCOMM上を約240バイト単位のUIHフレームに分割して送信（Bluetooth Classic / SPP、DLCI=2）。

```text
1D 47 59 04 30 00 ‹height/4, u16 LE› ... 1B 4A 50 1B BB BB 10 FF F1 45
```

### ビットマップ仕様

| 項目 | 値 |
|---|---|
| 幅 | 384 px（48 bytes/row） |
| 形式 | 1bit / モノクロ、MSBファースト、bit=1が黒 |
| 高さ | ヘッダー内の値 × 4（4行単位）。文字は常に92行固定、QRは内容に応じて可変 |

この仕様は実機テストで検証済み: 全18件の文字キャプチャ＋QR2件をビットマップとしてレンダリングし、
印字内容と目視で一致することを確認した（「A」「1234567890」「あいうえお」等）。
`tests/test_protocol_replay.py` では、実キャプチャの中身から再構成したコマンドが元のバイト列と
完全一致することを自動テストで保証している。

## 4. 未解決の問題：自前生成画像が4分割される

> **⚠ 未解決・QRコード印刷が実用不可**
> 自前で生成した画像データ（QRコード等）を送信すると、紙面に**横4分割**されて印字される。
> 実際にアプリが送信した本物のデータをそのまま再送すると、常に正しく1つだけ印字される。

送信経路とヘッダー生成ロジックが原因ではないことは、実データをそのまま再送して正常動作することで
証明済み。以下の要因を実機で個別に切り分けたが、いずれも決定要因ではなかった。

| 切り分けた要因 | 結果 |
|---|---|
| データサイズ（52〜1000行超） | 無関係 |
| `0xFF`バイト（全黒バイト）の有無 | 無関係 |
| パターンの複雑さ・規則性（単色/市松模様/斜め線/ランダムノイズ） | 無関係 |
| 実データと同じ92行に統一 | 無関係 |
| 実データの空白構造を残し中身だけ差し替え | 無関係（中身自体が原因と確定） |

「本物のアプリが生成したピクセルデータ」と「独自に生成したピクセルデータ」の間に、
何らかの未特定の違いがあると考えられる。詳細な調査記録は `docs/protocol_spec.md` の
「既知の未解決問題」セクションに全て残した。

### 次に試す価値がありそうなこと

- メーカー公式のSDK・開発者資料が入手できないか確認する（本調査は公式資料なしでの独自解析のため）
- ロジックアナライザで、生成データ送信時と実データ送信時のプリンター側の応答・タイミングを直接比較する
- 実キャプチャデータを「テンプレート」として複数の実キャプチャ文字を組み合わせる、実用上の代替手段を検討する
