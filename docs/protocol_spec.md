通信解析の結果を集約したプロトコル仕様書です。Python実装（`printer/`配下）はこの仕様に基づいて行います。
**不明な項目は推測で埋めず、「未確定」と記録すること。**

2026-08-26時点: ヘッダー・ビットマップ構造・幅・高さ・ビット順は **バイトレベルで解読済み**。
実際のビットマップをレンダリングして目視確認済み（`captures/rendered/contact_sheet.png`）。

**【2026-08-26 重要な訂正】** 本ドキュメントは当初「1bit白黒、48バイト/行」という仕様で
書かれていたが、これは誤りだった。本物のアプリ（`com.dingdang.newprint`）のAPKを逆コンパイル
した結果、正しくは**4階調グレースケール、1バイトに2画素（4bit/画素、値0〜3）、192バイト/行**
であることが判明した。48×4=192という数値の偶然の一致により、長期間「height×4=実際の行数」
という誤った（しかし辻褄が合ってしまう）解釈のまま実装・検証を進めてしまっていた。この誤りが、
自前生成画像が紙面に横4分割される既知の不具合の根本原因だった。下記の仕様は全て訂正済みの
正しい内容。旧仕様との違いや調査の経緯は末尾の「根本原因の判明と修正（2026-08-26）」を参照。

## Connection（確定）

| 項目 | 値 |
|---|---|
| Bluetooth方式 | **Classic（RFCOMM/SPP）**。BLE/GATTではない |
| Service UUID / Write Characteristic UUID | 該当なし（BLEでないため） |
| トランスポート | RFCOMM（DLCI=0が制御チャネル、DLCI=2がデータチャネル） |
| Write Type | RFCOMM UIHフレーム |

詳細は `docs/bluetooth_gatt.md` を参照。

## 印刷ジョブの全体構造（確定）

各印刷ジョブ（文字・QRとも共通）は、RFCOMM DLCI=2 のUIHフレーム列として送信される、以下の3部構成:

```text
[Header 8 bytes] + [Bitmap payload (height * 192 bytes)] + [Footer]
```

生データは `captures/rfcomm_jobs/` に保存済み（`job_00.bin`〜`job_17.bin`＝文字、`qr_ABC123.bin`／`qr_url.bin`＝QR）。
レンダリング結果は `captures/rendered/` を参照（全ジョブの内容を目視確認済み）。

### Header（8 bytes、確定・2026-08-26訂正）

| オフセット | サイズ | 内容 |
|---|---|---|
| 0-2 | 3 bytes | 固定値 `1D 47 59`（コマンド識別子。ASCII的には`GS G Y`、意味は独自コマンドと推定） |
| 3 | 1 byte | **階調数（gray_levels）**。実機キャプチャでは常に`04`（4階調グレースケール） |
| 4-5 | 2 bytes | 幅の参照値（リトルエンディアン u16）。**384px÷8=48が入るが、実際の行バイト数ではない**（下記参照。APK逆コンパイルで確認した1bit換算の名残の値） |
| 6-7 | 2 bytes | **高さフィールド（リトルエンディアン u16）。実際の行数そのもの**（4倍は不要。旧ドキュメントの記載は誤りだった） |

検証: 文字ジョブは全て高さフィールド=23 → 実行数=23行。QR(ABC123)は295行、QR(URL)は238行。
いずれも `(実データ長 - 8 - 10) ÷ 192` と完全一致する（192 = 実際の1行あたりバイト数）。

### Bitmap Payload（確定・2026-08-26訂正: 4階調グレースケール）

| 項目 | 値 |
|---|---|
| Width | **384 px** |
| 1行あたりバイト数（STRIDE） | **192 bytes/row = 384 ÷ 2**（1バイトに2画素、4bit/画素） |
| Height | ヘッダーの高さフィールドそのまま（4倍不要。文字は常に23行固定キャンバス、QRは内容により変動） |
| Format | **4階調グレースケール（2bit相当、値0〜3）**。1bit白黒ではない |
| 画素のパッキング | 1バイト = 2画素。上位ニブル(4bit)=左側の画素、下位ニブル(4bit)=右側の画素。各ニブルの値は0〜3のみ使用 |
| 画素値の意味 | **0 = 白（紙地）、3 = 黒（インク最大）**。値が大きいほど黒に近い（1bit方式のような単純反転ではない） |
| 縦方向 | 先頭バイトが画像の一番上の行 |

文字は常に384×23の固定キャンバスに描画され、内容（"A"〜"あいうえお"等）によって画素値のみが変わる。
QRコードは内容の複雑さに応じて高さフィールドが変動する（例: 短い文字列で295、長いURLで238。QRのバージョン/モジュール数に依存すると推測される。単純な文字数比例ではない）。

**なぜ旧ドキュメントは「1bit・48バイト/行・height×4」と誤って結論づけていたか:**
実際の1行は192バイトだが、旧実装は48バイト/行（1bit換算）で解釈しようとしていた。
`192 = 48 × 4` という数値が偶然一致するため、「ヘッダーの高さフィールド×4が実際の行数」という
辻褄の合う仮説を作ってしまい、`tests/test_protocol_replay.py`の単純な「バイト列を丸ごと
抽出して再構築する」テストでは矛盾が検出できなかった（総バイト数はどちらの解釈でも同じになるため）。
実際に生成した画像データを実機に送ると紙面に横4分割される、という不具合として初めて矛盾が露呈した。

## Image（文字・QRのキャプチャ結果、およびAPK逆コンパイルにより確定）

| 項目 | 値 |
|---|---|
| Width | **384 px（確定）** |
| Height（可変か固定か） | 可変（ヘッダーで直接指定、4の倍数である必要はない） |
| Format | **4階調グレースケール（値0〜3、1バイトに2画素）（確定）** |
| 画素値の意味 | 0=白、3=黒（確定） |
| 縦方向ビット順 | 先頭行から順（確定） |

写真のような多階調画像を送る場合、4階調に量子化する（`printer/image.py`の`to_gray4_bitmap()`は
`dither=True`でFloyd-Steinbergディザリングにも対応）。実機のSDK（逆コンパイルで確認）は
4階調モード（p19=4）では単純量子化（ディザリングなし）を使っていたが、写真の階調表現には
ディザリングを併用したほうが見栄えが良くなる可能性がある。

## 根本原因の判明と修正（2026-08-26）: 解決済み

**症状（解決済み）:** `printer/`ライブラリを使って自分で生成した画像データ（文字・QR等）を
実機に送信すると、紙面に横4分割された状態で印字される不具合が長期間未解決だった。一方、
`captures/rfcomm_jobs/`の実キャプチャデータをそのまま再送信した場合は常に正しく1つだけ
印字されていた。

**根本原因:** 本物のアプリ（`com.dingdang.newprint`、内部SDK名`com.luckprinter.sdk_new`）の
APKを取得・逆コンパイルしたところ、`PrinterImageProcessor.getBitmapByteArrayGray()`という
メソッドで実際の変換処理が見つかった。これにより、プロトコルの理解が根本的に誤っていたことが
判明した。

- **誤:** 1bit白黒、8画素/バイト、48バイト/行、ヘッダーの高さフィールド×4=実際の行数
- **正:** **4階調グレースケール、1バイトに2画素（4bit/画素、値0〜3）、192バイト/行**、
  ヘッダーの高さフィールドはそのまま実際の行数（×4は不要）

48×4=192という数値が偶然一致したため、「height×4」という辻褄の合う誤った解釈のまま
長期間実装・検証を続けてしまっていた。総バイト数はどちらの解釈でも同じになるため、
`tests/test_protocol_replay.py`の単純なバイト列再構築テストでは矛盾が検出できず、
実機に自前生成画像を送って初めて不具合として露呈していた。

正しい4階調グレースケール形式で実キャプチャデータ（`job_00.bin`＝「A」、`qr_ABC123.bin`、
`job4up_native.bin`＝QR4つ横並び）を再デコードしたところ、いずれも歪みのない正しい画像
（アンチエイリアスのかかった綺麗な文字、スキャン可能に見えるQRコード、4つの独立したQR
コードが正しく横に並んだ画像）として復元できることを確認した。

**修正内容:** `printer/protocol.py`（ヘッダー生成・STRIDE定数）、`printer/image.py`
（`to_1bit_bitmap()` → `to_gray4_bitmap()`：4階調量子化＋2画素/バイトのパッキングに全面書き換え）、
`printer/qr.py`（同上、QRを384px幅いっぱいにリサイズするよう変更）を修正した。修正後、
自前生成したQR・テキストのビットマップを新形式でレンダリングしたところ、いずれも正しい
1枚の画像として復元できることを確認した（`tests/`配下の自動テストも全て更新・PASS）。

### この不具合の調査で切り分けた要因（歴史的記録）

正しい原因（プロトコル自体の誤り）にたどり着くまでに、以下の要因を実機で個別に切り分けたが、
いずれも的外れだった（誤った1bit解釈の中で説明を探していたため）。

| 切り分けた要因 | 結果 |
|---|---|
| 送信経路（COMポート接続・チャンク分割・チャンク間ディレイ） | 無関係。実データはそのまま送れば正常動作 |
| データサイズ・行数（52行〜1200行超まで変化） | 無関係 |
| バイト値のドメイン（実データが16種類の値しか使わないという発見自体は正しかったが、単にマスクしても無関係） | 無関係 |
| パターンの複雑さ・規則性（単色/市松模様/斜め線/ランダムノイズ） | 無関係 |
| 送信幅（96px以内に収めても再現） | 無関係 |
| 余白（マージン、端に触れるかどうか） | 無関係 |
| 実データの空白構造を残し中身だけ差し替え | 無関係（中身自体ではなく解釈方法が誤りだった） |

振り返ると、「実データが16種類のバイト値しか使わない」という発見は、まさに**4階調
グレースケール（値0〜3）という正しい形式そのもの**を示す決定的な手がかりだったが、
当時は「1bitなのになぜか値が制限されている」という誤った枠組みで解釈しようとしたため、
真の原因（フォーマット自体が違う）にたどり着けなかった。最終的にAPK逆コンパイルという
質的に異なるアプローチに切り替えたことで解決した。

## 判定結論（重要・確定）

- Bluetooth方式: **Classic（RFCOMM/SPP）で確定**。BLEではない
- 文字は画像化されているか: **確定（目視確認済み）**。全パターンで文字形状が正しくビットマップとして再現された
- QRは専用コマンドか画像化か: **画像化で確定（目視確認済み）**。ノートエディタ経由のQR印刷も同一ビットマッププロトコルだった
- ビットマップ形式: **4階調グレースケール（1バイトに2画素、4bit/画素、値0〜3）で確定**（2026-08-26、APK逆コンパイルにより訂正。旧仕様の「1bit白黒」は誤り）
- 採用方式（手順書 30章の優先順位に基づく）: **文字・QRともにPython側で画像化し、共通の4階調グレースケールビットマッププロトコルで送信する（方式C・D）。** これにより実装は大幅に単純化される
- 4分割不具合: **解決済み**（上記「根本原因の判明と修正」参照）
- 残る未確定事項: フッターのチェックサム有無、パケット分割の正確な分割ロジック、写真等の多階調画像の実際の見栄え（ディザリングの要否）
