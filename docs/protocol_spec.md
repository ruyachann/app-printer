# Printer Protocol 仕様書（Phase 10, 13-14）

通信解析の結果を集約したプロトコル仕様書です。Python実装（`printer/`配下）はこの仕様に基づいて行います。
**不明な項目は推測で埋めず、「未確定」と記録すること。**

2026-08-26時点: ヘッダー・ビットマップ構造・幅・高さ・ビット順は **バイトレベルで解読済み**。
実際のビットマップをレンダリングして目視確認済み（`captures/rendered/contact_sheet.png`）。

## Connection（確定）

| 項目 | 値 |
|---|---|
| Bluetooth方式 | **Classic（RFCOMM/SPP）**。BLE/GATTではない |
| Service UUID / Write Characteristic UUID | 該当なし（BLEでないため） |
| トランスポート | RFCOMM（DLCI=0が制御チャネル、DLCI=2がデータチャネル） |
| Write Type | RFCOMM UIHフレーム |

詳細は `docs/bluetooth_gatt.md` を参照。

## 印刷ジョブの全体構造（確定）

各印刷ジョブ（文字・QRとも共通）は、RFCOMM DLCI=2 のUIHフレーム列として送信される、以下の3部構成:

```text
[Header 8 bytes] + [Bitmap payload (height*48 bytes)] + [Footer]
```

生データは `captures/rfcomm_jobs/` に保存済み（`job_00.bin`〜`job_17.bin`＝文字、`qr_ABC123.bin`／`qr_url.bin`＝QR）。
レンダリング結果は `captures/rendered/` を参照（全ジョブの内容を目視確認済み）。

### Header（8 bytes、確定）

| オフセット | サイズ | 内容 |
|---|---|---|
| 0-4 | 5 bytes | 固定値 `1D 47 59 04 30`（コマンド識別子。意味は未解析だが全ジョブ共通） |
| 5 | 1 byte | 固定値 `00`（未解析、常に0） |
| 6-7 | 2 bytes | **高さフィールド（リトルエンディアン u16）。単位は「4ピクセル行」**。実際の行数 = この値 × 4 |

検証: 文字ジョブは全て高さフィールド=23 → 実行数=92行。QR(ABC123)は295→1180行、QR(URL)は238→952行。
いずれも `(実データ長 - 8) ÷ 48` と完全一致し、幅48バイト固定という仮説を裏付けている。

### Bitmap Payload（確定）

| 項目 | 値 |
|---|---|
| Width | **384 px = 48 bytes/row（1bit per pixel）** |
| Height | ヘッダーの高さフィールド × 4（可変。文字は常に92行固定キャンバス、QRは内容により変動） |
| Format | 1bit monochrome |
| Byte order（横方向ビット順） | **MSBファースト**（バイトの最上位ビットが左端のピクセル） |
| 白黒 | **bit=1 → 黒（インク）、bit=0 → 白（紙地）** |
| 縦方向 | 先頭バイトが画像の一番上の行 |

文字は常に384×92の固定キャンバスに描画され、内容（"A"〜"あいうえお"等）によって黒ピクセルの位置のみが変わる。
QRコードは内容の複雑さに応じて高さフィールドが変動する（例: 短い文字列で295、長いURLで238。QRのバージョン/モジュール数に依存すると推測される。単純な文字数比例ではない）。

### Footer（一部確定）

| 項目 | 値 |
|---|---|
| 先頭バイト列 | `1B 4A 50 ...`（ESC/POSの `ESC J n`＝紙送りコマンドに類似した構造） |
| 詳細 | 続くバイト列の正確な意味（チェックサム有無等）は未解析 |

ジョブ間には短い制御フレーム（`01 10 ff` 等）が挟まることがある（ステータス確認/フロー制御と推定、詳細未解析）。

| 項目 | 値 |

| 分割単位 | 240 bytes単位で単純分割（ヘッダー・ビットマップ・フッターを連続バイト列とみなし、240バイトごとに区切って送信） |

| 終端マーカー | フッターの `1B 4A 50` 以降を参照 |
| チェックサム | 未確定 |

## 既知の未解決問題（重要）: 自前生成した画像データが4分割されて印字される

**症状:** 実機（Windows PC、COM4経由）で、`printer/`ライブラリを使って**自分で生成した**画像データ
（文字・QR・手作業で作った模様など）を送信すると、紙面に**横に4分割された状態**で印字される
（同じ内容が均等間隔で4回並ぶ）。一方、`captures/rfcomm_jobs/`の**実キャプチャデータをそのまま
再送信した場合は、常に正しく1つだけ**印字される。

### 調査で切り分けた事実（2026-08-26、実機テストにて）

| 検証内容 | 結果 |
|---|---|
| 送信経路（`PrinterConnection.connect()`/`write()`、チャンク分割、チャンク間ディレイ） | **正常**。実データを流すと問題なく動作する |
| `protocol.build_print_command()`（ヘッダー・フッター生成ロジック） | **正常**。実キャプチャの中身を渡すと実キャプチャとバイト単位で完全一致し（`tests/test_protocol_replay.py`）、実機でも正しく1つだけ印字される |
| 画像の総バイト数・行数（52行〜1000行超まで変化） | **無関係**。どのサイズでも自前生成データは4分割される |
| 0xFFバイト（8ピクセル全黒）の有無 | **無関係と判明**。0xFFを減らしても解決せず |
| データの複雑さ・規則性（単色/市松模様/斜め線/ランダムノイズ） | **無関係と判明**。ランダムノイズでも4分割される |
| PIL/qrcodeライブラリ経由か手作業で作ったバイト列か | **無関係**。PILを一切使わない手作業データでも再現する |
| 実データと同じ92行（本物の「A」と同サイズ）にしても | **解決せず**。サイズを合わせても自前生成データは4分割される |
| 本物の「A」データの空白部分は残し、文字部分だけ自前の模様に差し替え | **4分割される**。周囲の構造（空白配置）ではなく、書き換えた中身自体が原因と判明 |

### 追加調査（続報、2026-08-26）: 384px幅は実は4つの「96px区画」に分かれている

その後の実機テストで、さらに重要な手がかりが得られた。

1. **本物のアプリの「実データ」を詳細に解析したところ、黒（インク）部分は実は真っ黒(0xFF)ではなく、
   全体で黒画素比率わずか約8.6%程度の疎な網目模様（ハーフトーン）で構成されていた。** 均一な塗りつぶし
   は一切使われていない。
2. ノートエディタで**実際に「QRコードを4つ手動で横に並べて」印刷**してもらい、そのキャプチャを解析
   したところ、この4つのQRコードは1つのジョブ（384×348px）としてまとめて送信されており、
   問題なく正しく印字されることを確認した（実データはやはり複雑な内容でも常に正常動作する）。
3. **「左半分だけ黒」のシンプルな画像を送信したところ、紙面には「左右に均等な間隔で4つの小さな黒い
   四角」が印字された。** これは、1枚の画像全体が縮小されて4回複製されているように見える結果であり、
   単純な「バイト列の断片化」では説明が付かない。

これらから、**このプリンターは384px幅を4つの「96px区画」に物理的に分割して処理しており、
自前生成したデータ（384px幅の1本の連続したビットマップ行として送信）は、その4区画それぞれに
「圧縮コピー」されてしまっている**と考えられる。おそらく本物のアプリは、384px幅いっぱいの
内容を4区画それぞれに向けて個別にフォーマットして送信しているが、その正確なデータ配置方法
（インターリーブなのか、区画ごとの個別ヘッダーがあるのか等）はまだ特定できていない。

文字印刷（`print_text`）が実用上問題なく見えるのは、生成される文字画像の幅が384px全体ではなく
比較的狭い範囲に収まっていることが多く、4分割・圧縮されても視覚的な破綻が目立ちにくいためと
推測される。

### 結論

原因は「本物のアプリが生成したデータの区画別配置方法」と「私たちの単純な1本のビットマップ行と
しての送信方法」の間の違いにあると強く推測されるが、正確な配置ルール（各96px区画ごとにデータを
どう並べて送るか）はまだ解明できていない。サイズ・0xFF有無・パターンの規則性は決定要因ではないと
確認済みで、密度（ハーフトーン処理）を実データに寄せる試みでも完全解決には至っていない。

### 影響範囲

- **文字印刷（`print_text`）**: 実際に読める大きさで印刷できることを確認済みだが、幅の狭い文字は
  4分割の影響が視覚的に目立ちにくいだけで、理論上は同じ問題を抱えている可能性が高い
- **QR印刷（`print_qr`）**: 4分割されて出力され、実用上スキャンが困難。**未解決の既知の問題**
- **画像印刷（`print_image`）**: 同様の問題が起きる可能性が高いが未検証

### 引き継ぎ時に試すと良さそうなこと

- **最優先:** 本物のアプリに、384px幅いっぱいを使う「左右で内容が異なる」コンテンツ（例:
  長い文字列やノートエディタでの複数要素配置）を印刷させ、そのキャプチャを解析して、
  4つの96px区画それぞれにどうデータが配置されているか（インターリーブ方式なのか、
  区画ごとに独立したヘッダーがあるのか等）を特定する
- 実機のメーカー・型番（GKE Mini Pocket Printer S1-A20, FW V3.1.4）から公式SDK/開発者向け資料が
  入手できないか確認する（本調査は公式資料なしでの独自解析のため、正式仕様と食い違う可能性がある）
- 実キャプチャデータ（`captures/rfcomm_jobs/`）を「テンプレート」として、複数の実キャプチャ文字を
  組み合わせて任意の短い文字列を合成する回避策（本格的な原因究明ではないが実用上の代替手段）
- ロジックアナライザ等でBluetooth通信を直接モニタリングしながら、生成データ送信時と実データ送信時の
  タイミング・応答（Notification等）の違いを比較する

## 判定結論（重要・確定）

- Bluetooth方式: **Classic（RFCOMM/SPP）で確定**。BLEではない
- 文字は画像化されているか: **確定（目視確認済み）**。全パターンで文字形状が正しくビットマップとして再現された
- QRは専用コマンドか画像化か: **画像化で確定（目視確認済み）**。ノートエディタ経由のQR印刷も同一ビットマッププロトコルだった
- 採用方式（手順書 30章の優先順位に基づく）: **文字・QRともにPython側で画像化し、共通の1bitビットマッププロトコルで送信する（方式C・D）。** これにより実装は大幅に単純化される
- 残る未確定事項: フッターのチェックサム有無、パケット分割の正確な分割ロジック、写真等の多階調画像の実挙動（文字・QR以外は未検証）
