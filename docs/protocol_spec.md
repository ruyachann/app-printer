実際のビットマップをレンダリングして目視確認済み（`captures/rendered/contact_sheet.png`）。

## Connection（確定）

| 項目 | 値 |
|---|---|
| Bluetooth方式 | **Classic（RFCOMM/SPP）**。BLE/GATTではない |
| Service UUID / Write Characteristic UUID | 該当なし（BLEでないため） |
| トランスポート | RFCOMM（DLCI=0が制御チャネル、DLCI=2がデータチャネル） |
| Write Type | RFCOMM UIHフレーム |

詳細は `docs/bluetooth_gatt.md` を参照。

## 印刷ジョブの全体構造（確定）

各印刷ジョブ（文字・QRとも共通）は、RFCOMM DLCI=2 のUIHフレーム列として送信される、以下の3部構成:

```text
[Header 8 bytes] + [Bitmap payload (height*48 bytes)] + [Footer]
```

生データは `captures/rfcomm_jobs/` に保存済み（`job_00.bin`〜`job_17.bin`＝文字、`qr_ABC123.bin`／`qr_url.bin`＝QR）。
レンダリング結果は `captures/rendered/` を参照（全ジョブの内容を目視確認済み）。

### Header（8 bytes、確定）

| オフセット | サイズ | 内容 |
|---|---|---|
| 0-4 | 5 bytes | 固定値 `1D 47 59 04 30`（コマンド識別子。意味は未解析だが全ジョブ共通） |
| 5 | 1 byte | 固定値 `00`（未解析、常に0） |
| 6-7 | 2 bytes | **高さフィールド（リトルエンディアン u16）。単位は「4ピクセル行」**。実際の行数 = この値 × 4 |

検証: 文字ジョブは全て高さフィールド=23 → 実行数=92行。QR(ABC123)は295→1180行、QR(URL)は238→952行。
いずれも `(実データ長 - 8) ÷ 48` と完全一致し、幅48バイト固定という仮説を裏付けている。

### Bitmap Payload（確定）

| 項目 | 値 |
|---|---|
| Width | **384 px = 48 bytes/row（1bit per pixel）** |
| Height | ヘッダーの高さフィールド × 4（可変。文字は常に92行固定キャンバス、QRは内容により変動） |
| Format | 1bit monochrome |
| Byte order（横方向ビット順） | **MSBファースト**（バイトの最上位ビットが左端のピクセル） |
| 白黒 | **bit=1 → 黒（インク）、bit=0 → 白（紙地）** |
| 縦方向 | 先頭バイトが画像の一番上の行 |

文字は常に384×92の固定キャンバスに描画され、内容（"A"〜"あいうえお"等）によって黒ピクセルの位置のみが変わる。
QRコードは内容の複雑さに応じて高さフィールドが変動する（例: 短い文字列で295、長いURLで238。QRのバージョン/モジュール数に依存すると推測される。単純な文字数比例ではない）。

### Footer（一部確定）

| 項目 | 値 |
|---|---|
| 先頭バイト列 | `1B 4A 50 ...`（ESC/POSの `ESC J n`＝紙送りコマンドに類似した構造） |
| 詳細 | 続くバイト列の正確な意味（チェックサム有無等）は未解析 |

ジョブ間には短い制御フレーム（`01 10 ff` 等）が挟まることがある（ステータス確認/フロー制御と推定、詳細未解析）。

## パケット分割（RFCOMM）

| 項目 | 値 |
|---|---|
| 1パケット最大サイズ | 約240 bytes（RFCOMM UIHフレームのペイロード、MTU起因と推定） |
| 分割単位 | 240 bytes単位で単純分割（ヘッダー・ビットマップ・フッターを連続バイト列とみなし、240バイトごとに区切って送信） |
| シーケンス番号の有無 | 確認できず（なしと推定） |
| 終端マーカー | フッターの `1B 4A 50` 以降を参照 |
| チェックサム | 未確定 |
| ACK/Notificationの有無 | RFCOMM自体がACK付き信頼性転送のため、アプリケーション層でのACKは不要と推定 |

## 画像開始/終了コマンド

| 項目 | 値 |
|---|---|
| 画像開始コマンド | ヘッダー `1D 47 59 04 30 00 [height_LE_u16]` |
| 画像終了コマンド | フッター `1B 4A 50 ...`（用紙送り相当） |

## 判定結論（重要・確定）

- Bluetooth方式: **Classic（RFCOMM/SPP）で確定**。BLEではない
- 文字は画像化されているか: **確定（目視確認済み）**。全パターンで文字形状が正しくビットマップとして再現された
- QRは専用コマンドか画像化か: **画像化で確定（目視確認済み）**。ノートエディタ経由のQR印刷も同一ビットマッププロトコルだった
- 採用方式（手順書 30章の優先順位に基づく）: **文字・QRともにPython側で画像化し、共通の1bitビットマッププロトコルで送信する（方式C・D）。** これにより実装は大幅に単純化される
- 残る未確定事項: フッターのチェックサム有無、パケット分割の正確な分割ロジック、写真等の多階調画像の実挙動（文字・QR以外は未検証）
